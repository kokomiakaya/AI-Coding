# 注释审查技能（comment-review）

给代码做「说明书质检」：查有没有必要的注释 → 查注释和代码对不对得上 → 交中文报告。

只做检查和报告，不擅自改代码；补注释、改注释的建议在报告里列出，用户点头后再动手。

## 步骤

### 1. 确定审查范围
- 用户指定了文件/目录 → 查它
- 未指定 → 优先查当前未提交的改动（`git status` + `git diff`），其次按模块查
- 目标过宽时（如整个项目），按模块分次查（数据库层、界面层等），每次只查一个模块

### 2. 检查「必要的注释」是否缺失
判断标准：站在**没参与过本项目的新人**视角，只看代码能否看懂。需要注释的位置：

- **文件开头**：有没有一句话说明「这个文件是干什么的」（参考 `snake-engine.ts` 开头的说明风格）
- **关键入口/数据流**：本项目的主进程接口（`src/main/index.ts` 各 handler）、数据库层（`src/main/db.ts` 建表和查询）、预加载传话筒（`src/preload/index.ts` 的 window.api）——新人按「代码结构地图」找代码时，这些地方要有路标
- **难懂的代码**：复杂算法、正则、位运算、「魔法数字」（没有名字的常数）、特殊的边界处理——重点解释**为什么这么写**，而不是复述代码在做什么
- **跨文件约定**：金额单位「分」、日期格式 YYYY-MM-DD、接口返回 `{ ok, ... }` 这类约定，在关键位置有没有提醒
- **不要求注释**：显而易见的代码（简单取值、简单循环）不强制注释；不追求逐行注释，注释贵在「必要」而非「多」

### 3. 检查注释和代码是否对得上（过期注释）
- 注释里的参数名、字段名、常量值，代码已经改了而注释没改
- 注释写「上面/下面/后面」，但代码顺序已经变了
- 注释描述的用途和函数实际行为不一致（如注释说「返回元」，实际返回的是「分」）
- 改名、重构、删功能后留下的「孤儿注释」（注释还在，代码没了）

### 4. 其他注释质量问题
- 空话注释：「初始化」「开始」「处理数据」这类没有信息量的
- 被注释掉的大段代码：建议删除还是保留，给出理由
- 风格不一致：本项目代码注释风格是全中文，夹杂大段英文或中英混杂的提出来
- TODO/FIXME 标记：留给未来的坑，提醒用户注意

### 5. 生成中文注释审查报告
用以下格式向用户汇报（这是给用户的报告，不是开发者的原始输出）：

```
📝 注释审查报告

📋 审查范围：<文件/目录>
✅ 注释合格：N 处
⚠️ 问题：N 处

<逐条列出，按严重程度：>
🔴 必须补：文件:行号 — 缺什么注释、为什么别人会看不懂
🟡 建议补：文件:行号 — 建议加什么说明（可选）
🟢 需修正：文件:行号 — 注释和代码对不上：代码实际是……，注释却说……

📌 结论：<注释齐全 / 建议补充后再继续 / 需修正 N 处>
```

### 6. 收尾
- 报告后按用户要求补注释/改注释（用户点头才动手；补注释不改变代码逻辑）
- 判断「必要」时始终站在新人视角，宁缺毋滥
- 如产生了新的技术决策（注释规范等），记入 CLAUDE.md 决策表（按项目规则）
